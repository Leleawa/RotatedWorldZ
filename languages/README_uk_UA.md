# RotatedWorldZ

Версія RotatedWorld на 20 мовах програмування (плагін Paper/Folia, який повертає весь світ на 90° навколо осі X для гравців за допомогою PacketEvents):
Скомпільовано **Java, Kotlin, Scala 3, Gosu, Groovy, Kawa Scheme, Xtend, Fantom, Flix, Frege, Clojure, Haxe**,
плюс 8 скриптових шарів, що завантажуються під час виконання (runtime): **Kotlin Script, JRuby, JavaScript, Jython, Lua, BeanShell, Common Lisp, Prolog**, і все це зібрано в **один jar-файл**.


## Хто за що відповідає

| Рівень | Мова | Відповідальність | Чому саме вона |

| 0 api | Java | Контракти, які має реалізувати рівень чистих обчислень (лише типи JDK) | Найменший спільний знаменник, зрозумілий усім компіляторам |
| 1 Чисті обчислення | **Frege** | Алгебра координат: єдине канонічне визначення обертання плюс 10 властивостей QuickCheck | Чисті функції + вбудований QuickCheck; компілюється у `static int/float/double` методи без пакування (boxing) |
| | **Flix** | Правила іменування блоків (вертикальні ↔ настінні, типи блок-ентіті); очищення кешу | Таблиці правил + система ефектів гарантують чистоту; "які чанки ще комусь потрібні" — це правило **Datalog** |
| | **Clojure** | Парсинг конфігурації: елементи конфігурації записані як дані схеми | Керованість даними (data-driven): додати опцію = додати рядок даних |
| | **Haxe** | Обертання ніблових (nibble) масивів освітлення | Використовує лише `haxe.io.Bytes`, той самий код можна скомпілювати в JS/C++ (наприклад, автономний переглядач) |
| | **Fantom** | Стратегія пошуку безпечної точки опори під ногами | Чистий алгоритм, дивиться на світ крізь інтерфейс `BlockProbe`, не торкаючись Bukkit |

| 3 Рушій | **Scala 3** | Кеш чанків `ChunkStore` + рушій огляду `ViewManager` (плаваюча точка відліку / floating origin, попереднє завантаження, відправка чанків) | Ядро продуктивності, багато циклів по масивах |

| | **Groovy** | Оркестрація виконання команди `/rotate` | Холодний шлях (cold path) |
| | **Kawa Scheme** | Очищення кешу: збирає діапазони огляду для кожного світу та передає їх у Datalog мови Flix, щоб вирішити, які залишити (раніше було в `ViewManager` на Scala) | Попередня компіляція (AOT), обробка списків |
| | **Xtend** | `BlockRotation`: правила обертання BlockData | Автоматичне приведення типів `instanceof` + синтаксис властивостей; правила читаються як самі правила |
| 4 Плагін | **Kotlin** | Переписування пакетів (гарячий шлях netty), події Bukkit, векторний фасад PacketEvents | Оригінальний код; писати PacketEvents на Kotlin найзручніше |
| | Java | Точка входу плагіна (реалізує `Host`), міст для запуску Flix/Fantom/Clojure, завантажувач скриптових шарів | Точка входу та складання |
| 5 Скрипти | **Kotlin Script** | Рішення про перенесення плаваючої точки відліку (раніше в `ViewManager` на Scala) | Компілюється в байткод під час виконання, виклик кожного тіку не гальмує |
| | **JRuby** | Порядок відправки стовпців чанків (раніше в `ViewManager` на Scala) | Один ланцюжок `product.each_with_index.sort_by` |
| | **JavaScript** | Пропуск лагів "занадто швидкого переміщення" (раніше в слухачі Kotlin) | Інтерпретується через Rhino, події відбуваються рідко |
| | **Jython** | Відкидання (knockback) (раніше в слухачі Kotlin) | Виконується один раз на кожен отриманий удар |
| | **Lua** | Шкода від падіння (раніше в слухачі Kotlin) | Головний присяжний |
| | **BeanShell** | Рядок тексту для `/rotate status` (раніше в Groovy) | Скрипти з синтаксисом Java |
| | **Common Lisp** | Які серверні перевірки дозволено оминати поверненим гравцям (невдалі переміщення, кік за політ) (раніше в слухачі Kotlin) | Таблиця рішень `cond` |
| | **Prolog** | Граматика аргументів `/rotate`, записана як DCG (раніше в Groovy) | Граматику слід описувати за допомогою DCG |
| | **Усі вісім + Kawa** | **Журі присяжних щодо шкоди від падіння**: дев'ять мов рахують незалежно, перемагає більшість, при рівності голосів вирішує Lua, у разі розбіжностей записується попередження | Для розваги |

**Рівень 1 на етапі збірки взагалі не бачить Bukkit і PacketEvents** (вони отримують лише `api`), так само як і п'ять мов не бачать одна одну. Виклики вниз є звичайними викликами JVM; виклики вгору можуть відбуватися лише через інтерфейси: Flix та Fantom делегують реалізацію в `api.Services`, а головний клас плагіна надає сервіси для Рівня 3 через `kernel.Host`.

## Скриптові шари

Скрипти не компілюються у збірку, а завантажуються вбудованими інтерпретаторами під час запуску плагіна (`script.ScriptLayers`, 8 інтерпретаторів запускаються паралельно, приблизно 4–5 секунд):

* Сирцевий код розташований у `src/main/<kts|jruby|javascript|jython|lua|beanshell|commonlisp|prolog>/rules.*`, під час збірки він упаковується в директорію `scripts/` у jar-файлі.
* Якщо файл `plugins/RotatedWorldZ/scripts/<директорія>/rules.*` існує, він перевизначає версію з jar: **зміна правил не потребує перезбірки, достатньо перезапустити сервер**.
* Інтерфейси, які реалізують скрипти, знаходяться в `api.ScriptedRules`. Останній вираз у Kotlin Script має бути об'єктом, що одночасно реалізує і `Recenter`, і `FallJuror`, причому він не може бути анонімним об'єктом; решта скриптів лише оголошують глобальні функції (у Prolog — предикати, де останній аргумент є результатом), які огортаються в інтерфейси за допомогою Java.
* Вбудовані інтерпретатори не гарантують потокобезпечність (thread safety), виклики до кожного скрипта виконуються послідовно (`synchronized`). Тому лише Kotlin Script (виконання скомпільованого коду) перебуває на гарячому шляху кожного тіку, тоді як решта знаходяться на холодних шляхах.
* Бібліотеки на зразок jnr/jffi, що постачаються разом із Jython, мають конфлікт версій із JRuby, тому під час збірки Jython спочатку пакується окремо з релокацією цих пакетів (завдання `jythonIsolated`, за зразком апстрім-шаблону).

Кілька аспектів, що гарантують міжмовну узгодженість:

* Відображення граней блоків (UP→NORTH……) більше не прописується вручну; як Xtend (Bukkit `BlockFace`), так і Kotlin (PacketEvents `BlockFace`) виводяться з того самого обертання Frege.
* Відображення координат усередині секції `Geometry.localIndex` (Frege) та обертання освітлення Haxe використовують абсолютно однакове відображення, що звіряється комірка за коміркою у `smokeTest`.

## Збірка

```bash
./gradlew build          # Результат: build/libs/RotatedWorldZ-1.0.0.jar; включає checkGeometry та smokeTest
./gradlew checkGeometry  # Запуск лише перевірок властивостей QuickCheck мови Frege
./gradlew smokeTest      # Сервер не потрібен: запускає рівень чистих обчислень із готового jar і порівнює поведінку з оригінальним Kotlin, перевіряючи зв'язування решти рівнів
```

Під час виконання на сервері має бути встановлено PacketEvents (`depend: [packetevents]`).

Перша збірка завантажує Flix, Haxe та Fantom у папку `.tools/` (близько 60 МБ), Haxe також потребує JDK 8 (використовується лише його `rt.jar`; якщо Gradle toolchain його не знайде, він завантажиться автоматично через foojay). Для всього іншого використовується JDK 21.

## Підводні камені та нюанси кожної мови

* **Flix**: Може експортувати лише одну точку входу, згенеровану в класі `Main` дефолтного пакета (`FlixBridge` викликає її через рефлексію). Вона також генерує близько 500 класів і пакетів у кореневому каталозі (`Array`, `List`……), що може перекрити власні `Array`/`List` у Scala/Kotlin, тому вихідні файли Flix **не входять до жодного classpath компіляції**, а потрапляють лише в runtime і jar. Охоронець (guard) у Datalog захоплює щонайбільше 5 змінних. Інтерфейси Java та модулі Flix не можуть мати однакових імен.
* **Frege**: Параметри за замовчуванням є лінивими (lazy, у сигнатурах Java це `Lazy<Float>`); щоб отримати строгі параметри примітивних типів, додайте `!` до шаблону.
* **Fantom**: Реалізація інтерфейсів Java з дефолтними методами призводить до аварійного завершення (crash), тому інтерфейси в `api` не містять дефолтних методів. Типи Java `long`/`double`/`boolean` напряму відповідають типам Fantom `Int`/`Float`/`Bool`, усі посилальні типи можуть бути null (nullable). Літерали з рухомою комою слід писати як `0.5f` (`0.5` сприймається як Decimal).
* **Gosu**: `block` є ключовим словом (лямбда у Gosu). gosuc негайно резолвить типи анотацій, тому classpath компіляції повинен містити залежності Paper API: `org.jetbrains:annotations` та `jspecify`.
* **Xtend**: `Keyed` у Bukkit має одночасно `key()` і `getKey()`, тому `b.key` викликає неоднозначність; слід писати `b.getKey`. Якщо поле і метод мають однакову назву, ідентифікатор у тілі методу вказує на метод.
* **Haxe**: Цільова платформа `--jvm`; зовнішній завантажувач класів Java розпізнає лише `rt.jar` від JDK 8; `haxelib` в офіційному пакунку для Windows залежить від Neko, тому під час збірки в PATH розміщується заглушка (stub).
* **Clojure**: Покладається на завантажувач класів контексту потоку (Thread Context ClassLoader) для пошуку просторів імен; `ClojureBridge` тимчасово спрямовує його на завантажувач класів плагіна під час ініціалізації та викликів.
* **Kotlin Script**: Результатом скрипта не може бути анонімний об'єкт (`object : X {}` викликає помилку "anonymous type"), спочатку потрібно оголосити іменований клас.
* **Kawa**: Значення `null` із Java у Scheme є істинним (truthy, хибним є лише `#f`), перевірку слід писати як `(eq? x #!null)`; `obj:field` зчитує поле, `(obj:method)` викликає метод.
* **Завантажувач класів контексту потоку (Thread Context ClassLoader)**: Завантажувач контексту серверних потоків (головний потік, регіональні потоки, netty, глобальний планувальник) не бачить класів плагіна, тоді як середовища Kawa та Clojure використовують саме його для пошуку класів за іменем. Тому кожна точка входу із серверних потоків у ці середовища виконання обгортається через `kernel.PluginContext` (очищення кешу Kawa, журі, усі виклики скриптів, пошук опори у Gosu/Fantom, команди Groovy). Головний потік у `smokeTest` відповідно встановлює завантажувач контексту на завантажувач платформи (platform loader), імітуючи серверні потоки.
* **Prolog**: tuProlog за замовчуванням не завантажує DCG, необхідно викликати `loadLibrary(new DCGLibrary())`, щоб з'явилися `-->` та `phrase/2`.
* **Jython**: `PyString` — це байтовий рядок Python 2; якщо шлях містить китайські або non-ASCII символи, потрібно використовувати `Py.newStringOrUnicode`. Через це `smokeTest` запускається з non-ASCII шляху на зразок `build/smoke/插件 plugins/`.
* **Common Lisp (ABCL)**: Під час ініціалізації намагається використати рефлексію для відкриття фабрики віртуальних потоків JDK; без прапорця `--add-opens java.base/java.lang` друкує рядок у `System.err` (через що Paper видає попередження про "використання System.err плагіном"). Це безпечно, і `StderrFilter` перехоплює лише цей єдиний рядок під час ініціалізації ABCL.
* **Журі (Jury)**: `ceil(2.5 - 3)` повертає `-0.0`, функція `max` у Python / Kotlin / Scheme зберігає його без змін; перед підрахунком голосів значення слід нормалізувати до `0.0`, інакше при падінні на 2–3 блоки помилково видаватиметься попередження про "розбіжність думок".
* **Gosu**: Щойно середовище виконання ініціалізується, воно відкриває `java.base` для рефлексії, після чого проблеми з рефлексією в інших бібліотеках стає неможливо помітити. Тому `smokeTest` повторює послідовність `onEnable` плагіна: спочатку завантажує скриптові шари, і лише потім торкається Gosu. Команда `./gradlew smokeTest -PsmokeJava=25` дозволяє провести перевірку з використанням тієї ж версії JDK, що й на сервері.
* **JRuby**: `sort_by` є нестабільним сортуванням (unstable); щоб зберегти початковий порядок, індекс необхідно включити до ключа сортування.
* **Scala 3**: Після видалення сирцевих файлів інкрементна компіляція може залишити застарілі файли `.tasty`, які потрапляють у кеш збірки. Якщо у готовому jar виявлено зайві класи, виконайте `./gradlew clean build --rerun-tasks` один раз.

## Перевірено / Не перевірено

Перевірено (Windows 11, JDK 21, Gradle 9.7.1):

* Усі 12 компільованих мов успішно компілюються, усі 8 скриптових шарів успішно завантажуються, `./gradlew clean build --rerun-tasks` завершується успішно.
* `checkGeometry`: 10 властивостей QuickCheck пройдено, включаючи зворотне перетворення (roundtrip), узгодженість сітки/точок, відповідність повороту кута огляду повороту вектора, та те, що `zBase` є діленням з округленням донизу (floor division).
* `smokeTest` (загалом 123 134 перевірки, виконувані в ізольованому завантажувачі класів зі шляху, що містить китайські ієрогліфи для імітації завантаження плагіна; перевірено на JDK 21 та 25):
  * Результати правил Flix, конфігурації Clojure, освітлення Haxe, пошуку Fantom повністю відповідають оригінальній реалізації на Kotlin пункт за пунктом;
  * Результати 8 скриптів та Kawa повністю відповідають оригінальному коду, який вони замінили, 9 голосів журі одноголосно зійшлися без жодних попереджень; під час завантаження скриптових шарів у `System.err` нічого не виводиться;
  * Шари Scala/Gosu/Groovy/Xtend/Kotlin коректно зв'язуються, середовища виконання Gosu/Groovy/Scala успішно ініціалізуються.

**Не перевірено**:

* Не тестувалося на реальному сервері Paper / Folia, і жоден клієнт не заходив на сервер (для цього потрібно прийняти Minecraft EULA та встановити PacketEvents). Серверозалежні шляхи, такі як переписування пакетів, відправка чанків і повторне центрування, гарантуються лише перевірками компілятора та "построковим портуванням з оригіналу". Перед розгортанням обов'язково перевірте роботу на тестовому сервері.
* Розмір jar-файлу становить близько 231 МБ (оригінал 4.9 МБ): включає компілятор Kotlin, JRuby, Jython, ABCL, а також середовища виконання Gosu, Groovy, Scala, Clojure, Frege, Kawa. Запуск плагіна займає додаткові 4–5 секунд на завантаження скриптових шарів. Ці бібліотеки запаковані у вихідному вигляді без релокації: якщо на тому ж сервері інші плагіни використовують інші версії Kotlin/Scala/Groovy, можливі конфлікти.

## Структура каталогів

```
src/api/java        Рівень 0: Контракти рівня чистих обчислень (типи JDK)
src/kernel/java     Рівень 2: Спільний стан та інтерфейси сервісів (Bukkit + PacketEvents)
src/main/<мова>     Сирцевий код для кожної мови (скриптові шари у src/main/{kts,jruby,javascript,jython,lua,beanshell,commonlisp,prolog})
src/main/resources  plugin.yml, config.yml
buildSrc            Завдання компіляції Gradle для кожної мови
build.gradle.kts    Розподіл за рівнями та залежності
```
