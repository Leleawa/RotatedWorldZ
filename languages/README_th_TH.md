# RotatedWorldZ

เวอร์ชัน 20 ภาษาของ RotatedWorld (ปลั๊กอิน Paper/Folia ที่ใช้ PacketEvents เพื่อหมุนโลกทั้งใบ 90° รอบแกน X ให้ผู้เล่นมองเห็น):
คอมไพล์ **Java, Kotlin, Scala 3, Gosu, Groovy, Kawa Scheme, Xtend, Fantom, Flix, Frege, Clojure, Haxe** เข้ามาโดยตรง,
พร้อมด้วยเลเยอร์สคริปต์ 8 ภาษาที่โหลดตอนรันไทม์ ได้แก่ **Kotlin Script, JRuby, JavaScript, Jython, Lua, BeanShell, Common Lisp, Prolog** รวมทั้งหมดเป็น **jar เดียว**

| | **Common Lisp** | การตรวจสอบฝั่งเซิร์ฟเวอร์ใดบ้างที่จะยกเว้นให้ผู้เล่นที่หมุนตัว (การเคลื่อนที่ล้มเหลว, เตะออกฐานบิน) (เดิมอยู่ในลิสเนอร์ของ Kotlin) | ตารางการตัดสินใจแบบ `cond` |

**เลเยอร์ที่ 1 ตอนบิลด์จะไม่เห็น Bukkit และ PacketEvents เลย** (พวกมันได้รับเฉพาะ `api` เท่านั้น) และทั้งห้าภาษานี้ก็มองไม่เห็นซึ่งกันและกัน การเรียกใช้งานลงด้านล่างเป็นการเรียก JVM ปกติ ส่วนการเรียกขึ้นด้านบนทำได้ผ่านอินเทอร์เฟซเท่านั้น: Flix และ Fantom มอบหมายการอิมพลีเมนต์ให้กับ `api.Services` และคลาสหลักของปลั๊กอินจะให้บริการแก่เลเยอร์ที่ 3 ผ่าน `kernel.Host`

## เลเยอร์สคริปต์

สคริปต์ไม่ได้ถูกคอมไพล์รวมเข้ามา แต่จะถูกโหลดโดยอินเทอร์พรีเตอร์แบบฝังตัวเมื่อปลั๊กอินเริ่มทำงาน (`script.ScriptLayers`, อินเทอร์พรีเตอร์ 8 ตัวเริ่มทำงานแบบขนาน ใช้เวลาประมาณ 4–5 วินาที):

* ซอร์สโค้ดอยู่ที่ `src/main/<kts|jruby|javascript|jython|lua|beanshell|commonlisp|prolog>/rules.*` ตอนบิลด์จะถูกแพ็กลงในโฟลเดอร์ `scripts/` ภายใน jar
* หากมี `plugins/RotatedWorldZ/scripts/<ไดเรกทอรี>/rules.*` อยู่ ระบบจะนำไฟล์นั้นไปเขียนทับไฟล์ใน jar: **แก้ไขกฎได้โดยไม่ต้องบิลด์ใหม่ เพียงแค่รีสตาร์ตเซิร์ฟเวอร์ก็พอ**
* อินเทอร์เฟซที่สคริปต์ต้องอิมพลีเมนต์อยู่ใน `api.ScriptedRules` นิพจน์สุดท้ายของ Kotlin Script จะต้องเป็นออบเจกต์ที่อิมพลีเมนต์ทั้ง `Recenter` และ `FallJuror` พร้อมกัน และต้องไม่ใช่ออบเจกต์นิรนาม (anonymous object) ส่วนสคริปต์ที่เหลือกำหนดเพียงฟังก์ชันส่วนกลางเท่านั้น (สำหรับ Prolog คือเพรดิเคต โดยอาร์กิวเมนต์สุดท้ายคือผลลัพธ์) ซึ่ง Java จะนำไปครอบเป็นอินเทอร์เฟซ
* อินเทอร์พรีเตอร์แบบฝังตัวทั้งหมดไม่รับประกันความปลอดภัยของเธรด (thread-safety) การเรียกใช้สคริปต์แต่ละตัวจึงเป็นแบบเรียงลำดับ (`synchronized`) ดังนั้นจึงมีเพียง Kotlin Script (รันแบบคอมไพล์) เท่านั้นที่อยู่บนฮอตพาธในทุก ๆ ทิก ส่วนที่เหลือล้วนอยู่บนโคลด์พาธ
* ไลบรารี jnr/jffi ที่ติดมากับ Jython มีปัญหารุ่นชนกันกับ JRuby ดังนั้นตอนบิลด์จึงต้องแพ็กเกจ Jython แยกต่างหากก่อน พร้อมกับทำการรีโลเคตแพ็กเกจเหล่านี้ (ทาสก์ `jythonIsolated` ตามแนวทางของเทมเพลตต้นทาง)

จุดสำคัญที่รับประกันความสอดคล้องกันข้ามภาษา:

* การจับคู่หน้าของบล็อก (UP→NORTH……) ไม่ต้องเขียนด้วยตนเองอีกต่อไป ทั้ง Xtend (Bukkit `BlockFace`) และ Kotlin (PacketEvents `BlockFace`) ล้วนคำนวณมาจากการหมุนแบบเดียวกันของ Frege
* การจับคู่พิกัดภายในเซกชัน `Geometry.localIndex` (Frege) และการหมุนแสงของ Haxe ใช้การจับคู่เดียวกัน และถูกตรวจสอบเทียบกันทีละช่องใน `smokeTest`

## การบิลด์

```bash
./gradlew build          # ผลลัพธ์: build/libs/RotatedWorldZ-1.0.0.jar; รวม checkGeometry และ smokeTest
./gradlew checkGeometry  # รันเฉพาะคุณสมบัติ QuickCheck ของ Frege
./gradlew smokeTest      # ไม่จำเป็นต้องมีเซิร์ฟเวอร์: เริ่มต้นเลเยอร์คำนวณล้วนจาก jar สำเร็จรูป และเทียบพฤติกรรมกับ Kotlin เดิม พร้อมตรวจสอบการลิงก์ของเลเยอร์อื่น ๆ
```

ตอนรันไทม์จำเป็นต้องติดตั้ง PacketEvents บนเซิร์ฟเวอร์ (`depend: [packetevents]`)

การบิลด์ครั้งแรกจะดาวน์โหลด Flix, Haxe, Fantom มาไว้ที่ `.tools/` (ประมาณ 60 MB) ส่วน Haxe ยังต้องการ JDK 8 เพิ่มเติม (ใช้เฉพาะ `rt.jar` เท่านั้น หาก Gradle toolchain หาไม่พบจะดาวน์โหลดให้อัตโนมัติผ่าน foojay) ส่วนที่เหลือทั้งหมดใช้ JDK 21

## จุดที่ต้องระวังในแต่ละภาษา

* **Flix**: ส่งออกฟังก์ชันจุดเริ่มต้นได้เพียงฟังก์ชันเดียว ซึ่งถูกสร้างขึ้นในคลาส `Main` ของดีฟอลต์แพ็กเกจ (`FlixBridge` เรียกใช้ผ่านการรีเฟลกชัน) นอกจากนี้ยังสร้างคลาสและแพ็กเกจประมาณ 500 รายการในรูทไดเรกทอรี (`Array`, `List`……) ซึ่งอาจไปบดบัง `Array`/`List` ของ Scala/Kotlin เอง ดังนั้นผลลัพธ์ของ Flix จึง**ไม่อยู่บน classpath การคอมไพล์ใด ๆ** แต่จะถูกนำไปใส่ไว้ในรันไทม์และ jar เท่านั้น การ์ด (guard) ของ Datalog จับตัวแปรได้สูงสุด 5 ตัว และอินเทอร์เฟซของ Java กับโมดูลของ Flix ห้ามใช้ชื่อซ้ำกัน
* **Frege**: พารามิเตอร์มีลักษณะแบบเลซี่ (lazy) โดยค่าเริ่มต้น (ในซิกเนเจอร์ของ Java จะเป็น `Lazy<Float>`) หากต้องการพารามิเตอร์ชนิดพรีมิทีฟแบบเข้มงวด (strict) ให้เติม `!` ในแพทเทิร์น
* **Fantom**: การอิมพลีเมนต์อินเทอร์เฟซ Java ที่มีดีฟอลต์เมธอดจะทำให้แครช ดังนั้นอินเทอร์เฟซใน `api` จึงไม่มีดีฟอลต์เมธอด `long`/`double`/`boolean` ของ Java จะจับคู่กับ `Int`/`Float`/`Bool` ของ Fantom โดยตรง และชนิดข้อมูลอ้างอิงทั้งหมดเป็นแบบ nullable ลิทเทอรัลจำนวนจริงทศนิยมต้องเขียนเป็น `0.5f` (`0.5` จะถือเป็น Decimal)
* **Gosu**: `block` เป็นคีย์เวิร์ด (แลมบ์ดาของ Gosu) gosuc จะแปลงชนิดของแอนโนเทชันทันที ดังนั้นใน classpath การคอมไพล์จึงต้องมี `org.jetbrains:annotations` และ `jspecify` ที่ Paper API จำเป็นต้องใช้
* **Xtend**: `Keyed` ของ Bukkit มีทั้ง `key()` และ `getKey()` พร้อมกัน ทำให้การเขียน `b.key` เกิดความกำกวม (ambiguous) จึงต้องเขียนเป็น `b.getKey` เมื่อฟิลด์และเมธอดมีชื่อเหมือนกัน ชื่อที่อยู่ภายในเนื้อเมธอดจะชี้ไปยังเมธอดเสมอ
* **Haxe**: ทาร์เก็ต `--jvm`; คลาสโหลดเดอร์ภายนอกของ Java รู้จักเฉพาะ `rt.jar` ของ JDK 8 เท่านั้น; `haxelib` ในแพ็กเกจ Windows อย่างเป็นทางการขึ้นอยู่กับ Neko จึงต้องวางสตัด (stub) ไว้ใน PATH ระหว่างการบิลด์
* **Clojure**: อาศัย Thread Context ClassLoader เพื่อค้นหาเนมสเปซ `ClojureBridge` จะสลับไปชี้ที่คลาสโหลดเดอร์ของปลั๊กอินชั่วคราวระหว่างการเตรียมการและการเรียกใช้
* **Kotlin Script**: ผลลัพธ์ของสคริปต์ต้องไม่ใช่ออบเจกต์นิรนาม (`object : X {}` จะแจ้งเตือนข้อผิดพลาด "anonymous type") จะต้องประกาศคลาสที่มีชื่อก่อนเสมอ
* **Kawa**: ค่า `null` ของ Java ในภาษา Scheme จะถือเป็นค่าความจริง (truthy โดยมีเพียง `#f` เท่านั้นที่เป็นเท็จ) การตรวจสอบต้องเขียนเป็น `(eq? x #!null)`; การอ่านฟิลด์ใช้ `obj:field` และการเรียกเมธอดใช้ `(obj:method)`
* **Thread Context ClassLoader**: คอนเท็กซ์คลาสโหลดเดอร์ของเธรดเซิร์ฟเวอร์ (เธรดหลัก, เธรดรีเจียน, netty, ตัวจัดคิวงานส่วนกลาง) จะมองไม่เห็นคลาสของปลั๊กอิน แต่รันไทม์ของ Kawa และ Clojure จำเป็นต้องใช้มันในการค้นหาคลาสตามชื่อ ดังนั้นทุกจุดที่เธรดเซิร์ฟเวอร์เข้าสู่รันไทม์เหล่านี้จึงถูกห่อหุ้มด้วย `kernel.PluginContext` (การล้างแคช Kawa, คณะลูกขุน, การเรียกใช้สคริปต์ทั้งหมด, Gosu/Fantom ค้นหาจุดยืน, คำสั่ง Groovy) เธรดหลักของ `smokeTest` จึงตั้งค่าคอนเท็กซ์คลาสโหลดเดอร์เป็นแพลตฟอร์มโหลดเดอร์เพื่อจำลองเธรดของเซิร์ฟเวอร์
* **Prolog**: tuProlog ไม่โหลด DCG โดยค่าเริ่มต้น ต้องเรียก `loadLibrary(new DCGLibrary())` ก่อนจึงจะใช้งาน `-->` และ `phrase/2` ได้
* **Jython**: `PyString` เป็นไบต์สตริงของ Python 2 หากพาธมีตัวอักษรภาษาจีนหรือ non-ASCII ต้องใช้ `Py.newStringOrUnicode` ดังนั้น `smokeTest` จึงถูกสั่งรันจากพาธที่เป็น non-ASCII เช่น `build/smoke/插件 plugins/`
* **Common Lisp (ABCL)**: เมื่อเตรียมการจะพยายามใช้รีเฟลกชันเพื่อเปิดเวอร์ชวลเธรดแฟกทอรีของ JDK หากไม่มีอาร์กิวเมนต์ `--add-opens java.base/java.lang` จะมีการพิมพ์หนึ่งบรรทัดลงใน `System.err` (ทำให้ Paper แจ้งเตือนว่า "ปลั๊กอินใช้ System.err") ซึ่งไม่มีผลเสียใด ๆ โดย `StderrFilter` จะดักจับเฉพาะบรรทัดนี้ไว้ระหว่างที่ ABCL กำลังเริ่มต้นทำงาน
* **คณะลูกขุน**: `ceil(2.5 - 3)` จะได้ผลลัพธ์เป็น `-0.0` ซึ่งฟังก์ชัน `max` ใน Python / Kotlin / Scheme จะคงค่านั้นไว้โดยตรง ก่อนการนับคะแนนจึงต้องปรับให้เป็น `0.0` เสียก่อน มิฉะนั้นเมื่อตกจากความสูง 2–3 บล็อกจะแจ้งเตือน "ความเห็นไม่ตรงกัน" อย่างผิดพลาด
* **Gosu**: ทันทีที่รันไทม์เริ่มทำงานจะเปิด `java.base` ให้กับรีเฟลกชัน หลังจากนั้นจะไม่สามารถตรวจพบปัญหาการรีเฟลกชันของไลบรารีอื่นได้ ดังนั้น `smokeTest` จึงจัดลำดับตาม `onEnable` ของปลั๊กอิน โดยโหลดเลเยอร์สคริปต์ก่อนแล้วจึงค่อยแตะต้อง Gosu และสามารถใช้คำสั่ง `./gradlew smokeTest -PsmokeJava=25` เพื่อทดสอบด้วย JDK เดียวกับที่เซิร์ฟเวอร์ใช้งานได้
* **JRuby**: `sort_by` เป็นการเรียงลำดับที่ไม่เสถียร (unstable) หากต้องการคงลำดับเดิมไว้ จะต้องรวมดัชนี (index) เข้าไปในคีย์การเรียงลำดับด้วย
* **Scala 3**: หลังจากลบไฟล์ต้นฉบับ การคอมไพล์แบบส่วนเพิ่ม (incremental compilation) อาจทิ้งไฟล์ `.tasty` เก่าไว้และหลุดเข้าไปในแคชการบิลด์ หากพบว่ามีคลาสที่ไม่ควรมีปรากฏอยู่ใน jar ให้รัน `./gradlew clean build --rerun-tasks` หนึ่งครั้ง

## ได้รับการตรวจสอบแล้ว / ยังไม่ได้รับการตรวจสอบ

ได้รับการตรวจสอบแล้ว (Windows 11, JDK 21, Gradle 9.7.1):

* ภาษาคอมไพล์ทั้ง 12 ภาษาคอมไพล์ผ่านทั้งหมด เลเยอร์สคริปต์ทั้ง 8 เลเยอร์โหลดผ่านทั้งหมด คำสั่ง `./gradlew clean build --rerun-tasks` ผ่านเรียบร้อย
* `checkGeometry`: คุณสมบัติ QuickCheck ทั้ง 10 ข้อผ่านการทดสอบ ซึ่งรวมถึงการเดินทางไป-กลับ (roundtrip), ความสอดคล้องระหว่างกริด/จุด, การหมุนมุมมองตรงกับการหมุนเวกเตอร์, `zBase` เป็นการหารแบบปัดเศษลง (floor division)
* `smokeTest` (การตรวจสอบทั้งหมด 123,134 รายการ ทำงานในคลาสโหลดเดอร์ที่แยกเดี่ยว จากพาธที่มีตัวอักษรภาษาจีนเพื่อจำลองการโหลดปลั๊กอิน; ทดสอบผ่านทั้งบน JDK 21 และ 25):
  * ผลลัพธ์ของกฎ Flix, คอนฟิก Clojure, แสง Haxe, การค้นหาของ Fantom สอดคล้องกับผลลัพธ์ของ Kotlin ต้นฉบับแบบข้อต่อข้อ
  * ผลลัพธ์ของ 8 สคริปต์และ Kawa สอดคล้องกับโค้ดต้นฉบับที่นำมาแทนที่แบบข้อต่อข้อ คณะลูกขุนทั้ง 9 เสียงเห็นพ้องต้องกันทั้งหมด ไม่มีการบันทึกคำเตือนใด ๆ และตอนโหลดเลเยอร์สคริปต์ไม่มีการพิมพ์ลงใน `System.err`
  * เลเยอร์ Scala/Gosu/Groovy/Xtend/Kotlin สามารถเชื่อมโยง (link) กันได้ปกติ รันไทม์ของ Gosu/Groovy/Scala เริ่มต้นทำงานได้อย่างถูกต้อง

**ยังไม่ได้รับการตรวจสอบ**:

* ยังไม่ได้รันบนเซิร์ฟเวอร์ Paper / Folia จริง และยังไม่มีไคลเอนต์ล็อกอินเข้าสู่เซิร์ฟเวอร์ (จำเป็นต้องยอมรับ Minecraft EULA และติดตั้ง PacketEvents) ส่วนการทำงานที่ต้องพึ่งพาเซิร์ฟเวอร์อย่างการเขียนแพ็กเก็ตใหม่ การส่งชังก์ และการย้ายตำแหน่ง ได้รับการรับรองผ่านการตรวจสอบการคอมไพล์และการ "พอร์ตบรรทัดต่อบรรทัดจากต้นฉบับ" เท่านั้น โปรดทดสอบบนเซิร์ฟเวอร์ทดสอบก่อนนำไปใช้งานจริง
* ไฟล์ jar มีขนาดประมาณ 231 MB (ต้นฉบับ 4.9 MB): ประกอบด้วยคอมไพเลอร์ Kotlin, JRuby, Jython, ABCL รวมทั้งรันไทม์ของ Gosu, Groovy, Scala, Clojure, Frege, Kawa การเริ่มทำงานของปลั๊กอินจะใช้เวลาเพิ่มขึ้น 4–5 วินาทีในการโหลดเลเยอร์สคริปต์ รันไทม์เหล่านี้ถูกแพ็กรวมเข้ามาตามสภาพเดิมโดยไม่มีการ relocate: หากเซิร์ฟเวอร์เดียวกันมีปลั๊กอินอื่นที่มี Kotlin/Scala/Groovy เวอร์ชันต่างกัน อาจเกิดข้อขัดแย้งขึ้นได้

```
src/api/java        เลเยอร์ที่ 0: สัญญาของเลเยอร์คำนวณล้วน (ชนิดข้อมูล JDK)

src/main/<ภาษา>      ซอร์สโค้ดของแต่ละภาษา (เลเยอร์สคริปต์อยู่ที่ src/main/{kts,jruby,javascript,jython,lua,beanshell,commonlisp,prolog})
src/main/resources  plugin.yml, config.yml
buildSrc            ทาสก์การคอมไพล์ Gradle ของแต่ละภาษา
build.gradle.kts    การแบ่งเลเยอร์และดีเพนเดนซี
```
